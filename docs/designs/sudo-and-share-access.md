# Design: Sudo and Share Access

## Problem Statement
The user wants one Telegram userbot account to serve their own quick tasks and let other Telegram accounts safely use selected tools through DMs and groups. The current managed commands are owner-filtered; there is no database-backed model for sudo users, share users, or standalone command grants. The existing inline `.help` menu is already the desired guided interface and should show users which commands they can and cannot use.

## What Makes This Cool
The same userbot can be a personal toolkit and a deliberate, scoped command service for friends: a person opens `.help`, sees what is available to them, taps a button owned by their own Telegram ID, and runs an allowed tool in the chat where they need it. `?` and `#` make the delegated access path visible without pretending that a prefix alone grants permission.

## Constraints
- Keep the existing guided `.help` menu; do not build a second help interface.
- The first share set is `.say` and `.tts`, usable in DMs and groups. Add `.ai` later.
- Sudo has `#` prefix and starts with `.eval` and `.exec`; trusted sudo users may manage explicit command grants.
- Owner uses `.`, sudo uses `#`, and share users or standalone command-grant users use `?`.
- A message sender is eligible for dispatch only if they are the owner, sudo user, share user, or have an explicit command grant. Check the proper prefix and then command permission. If any check fails, silently return.
- A standalone command grant is sufficient for that command; it does not add a share or sudo role. `.allow` can grant any command in the first version, including powerful commands. This is intentionally permissive and must be called out as a follow-up safety concern.
- `.allow` adds requested `(user_id, command)` rows; report added and already-existing grants. `.disallow` removes only explicit grants and reports removed versus never-granted entries. `.resetallow` clears that user’s explicit grants. Removing explicit grants must not remove role-based access.
- The user specified sudo management `.addsudo`, `.rmsudo`, `.sudolist`; add/remove/list share management is expected (the user explicitly added share removal). User resolution should support reply, mention, or numeric ID as described for sudo.
- Every bot-generated callback button is bound to the initiating Telegram user ID. For managed callback handlers, enforce this centrally in the callback wrapper; for generated buttons from any other path, use the same callback-data builder and owner-check helper. Buttons that cannot carry or retrieve an initiator identity are not exposed to delegated users. Callback ID is an ownership check, not a secret and not a permission grant. Keep callback data within Telegram’s platform limit.
- Overlapping permissions use the prefix for the explicit access path: `.` is owner-only, `#` selects sudo authorization, and `?` selects share membership or a standalone command grant. Each prefix then requires the corresponding current role/grant and command declaration; possession of multiple roles does not make a different prefix valid. Help marks a command available when any path the viewer possesses is supported for it, and spoiler-hides it otherwise.
- Help shows commands a user cannot invoke as spoilered entries and adds a bold blockquote footer explaining that spoilered commands are unavailable to them.
- Only the owner can have their command-trigger message edited or deleted by owner-oriented handlers. For sudo/share/grant users, send results to the chat as a reply or new message rather than editing/deleting their message. Unlisted senders’ command requests remain ignored.
- Use PostgreSQL through a SQLAlchemy provider and migrations; starting schema covers sudoers, share users, and `allowed_cmds(user_id, command)` with the user/command pair as primary key. Database URL, missing-database provisioning, migration framework, and startup failure policy remain to be decided during technical planning.

## Premises
1. Permission enforcement must use one authoritative central policy to avoid per-handler checks drifting or being omitted.
2. The callback user ID binds button ownership but never replaces fresh command authorization.
3. Prefixes indicate the requested access path; they do not grant access on their own.
4. Shared users receive only commands explicitly designated shareable, initially `.say` and `.tts`; sudo users receive commands explicitly designated sudo-enabled, initially `.eval` and `.exec`; explicit `allowed_cmds` grants independently authorize a named command.
5. Unauthorized command senders and wrong-prefix or disallowed requests are silently ignored.
6. Help deliberately reveals restricted command entries to sudo/share users through spoilers, with an explanatory bold blockquote.
7. SQL database credentials must be configured by the operator; creating application tables is distinct from provisioning a missing PostgreSQL database.

## Approaches Considered
### Approach A: Central managed authorization (selected)
Add access metadata to managed command declarations and route owner, sudo, share, standalone grants, prefix checks, and callback ownership through shared framework-level services. Back persistent state with SQLAlchemy/PostgreSQL and migrations. Use the same policy in help and runtime checks; make handlers aware of whether the sender is the owner so they do not edit/delete delegated users’ messages.

### Approach B: Provider plus handler checks
Centralize storage and permission lookup in an access provider, but require each opted-in command to invoke authorization and caller-aware behavior. This keeps framework changes smaller but allows runtime enforcement and help declarations to drift, and a missed check can expose a command.

### Approach C: Commands now, help callbacks only
Implement central command authorization and bind only help callbacks in the first delivery, generalizing callback ownership for other callback menus later. This narrows initial callback work but knowingly defers the user's stated all-buttons ownership requirement.

## Recommended Approach
Proceed with Approach A. The managed API and manager should own the common authorization boundary so future command declarations have one permission source. The access plugin should provide role/grant management, while database provider/migrations persist the records. Help should query the same effective-access policy used at dispatch. Use explicit route prefixes rather than inferring the route from the user's union of roles: `.` owner path, `#` sudo path, `?` share-or-grant path. A command may be help-visible if at least one route supported by that command is available to the viewer; execution still requires that route’s permission.

Callback-data encoding should be centralized and validated against Telegram’s maximum length; where action payload plus user ID cannot fit, use a compact opaque token/state record rather than truncating or omitting ownership. On callback, validate the real clicker against the encoded/stored initiator, then re-check any authorization needed for the action. Enforce in the managed callback wrapper and require every other delegated-facing button generator to use the same helper; if a callback surface cannot preserve/validate initiator identity, do not expose that surface to delegated users. Preserve owner-only message mutation and make delegated handlers reply instead.

## Open Questions
- What exact PostgreSQL environment variable and URL format should be documented?
- Should application startup create schema automatically, run migrations automatically, or fail unless a separate migration step has been run?
- What migration library should be used, and should the app be able to create the PostgreSQL database itself or only connect to a pre-provisioned database?
- What are the exact share management/list command names, and is a share-list command required?
- How should the `.allow` target user be resolved and validated when an ID is supplied versus reply/mention?
- Which owner-only administrative operations remain inaccessible even to sudo users?
- What is the intended error/recovery behavior when PostgreSQL is unavailable: fail startup, disable delegated access, or queue no state and silently deny delegated requests?
- Inventory non-managed callback buttons and ensure every delegated-facing generated button uses the common builder/owner check; otherwise it stays unavailable to delegated users.

## Risks and Follow-up
- Open command grants are powerful: a sudo manager can grant commands such as `.eval` or `.exec` directly to non-sudo users. The user explicitly accepts this for the first version; add a follow-up task to reconsider whether sudo grants should exclude owner-equivalent commands or require stronger confirmation.
- Telegram callback data has a small maximum size; adding a raw user ID to existing payloads can exceed it. Validate all callback-data constructions and use compact state-backed tokens where required.
- Shared command execution via the user account must not accidentally apply owner-only edits/deletes to another sender’s messages.
- With PostgreSQL as an access-control dependency, outage handling must fail closed for all non-owner access.
- Commands that include long-running or externally visible actions need tests proving sender identity, chat destination, prefix, and mutation behavior.

## Success Criteria
- Owner commands continue to work with the configured `.` prefix and preserve existing owner behavior.
- Authorized sudo users can use `#eval` and `#exec`; authorized share users can use `?say` and `?tts` in DMs and groups.
- A standalone `allowed_cmds` grant enables exactly the named command using `?`, without adding a role; `.disallow` and `.resetallow` remove only explicit grants.
- Ineligible sender, incorrect prefix, or missing permission produces no handler side effect and no permission-denied message.
- `.help` reflects effective access for the viewer, spoiler-hides commands they cannot invoke, and includes the requested bold blockquote footer.
- A generated button is usable only by the Telegram user who initiated its menu, including callbacks whose encoded/stored initiator is missing, malformed, stale, or mismatched (deny safely).
- Delegated handlers send their result in the relevant chat and do not edit/delete the sender’s command message; owner behavior remains unchanged.
- Database tables and migrations initialize/reach the expected schema on a fresh setup and an upgrade; duplicate adds and absent removals produce the specified status output.
- Automated tests cover direct, group, callback, prefix, grant/role intersection, database failure, and owner-versus-delegated message behavior.

## What I noticed about how you think
- You framed the use case as “one telegram account which my friend can use” for `.say`, `.tts`, and later AI, which kept the first version tied to real tasks.
- You separated shared tools from trusted access: “share as sharing command with users” and sudo as “same owner but using other account for access.”
- You explicitly chose silent failure for unauthorized senders and a visible prefix for each access path, making the interaction predictable without exposing denial messages.
- You accepted unrestricted first-version command grants while asking to capture the risk as a future todo, rather than silently changing the permission model.
